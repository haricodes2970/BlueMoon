# ADR-0026: BlueMoon Token — Atomic Single-Use Consumption, Separate from Auth Infrastructure

- **Date:** 2026-08-09
- **Status:** Accepted

## Context

Milestone 0.9 implements the BlueMoon Token, specified in
[Product-Requirements-Document.md](../product/Product-Requirements-Document.md#bluemoon-token):
generated by an account owner, single-use, expires after 300 seconds,
required alongside the recipient's username to establish a friendship
-- a username alone must never be sufficient. Two implementation
questions weren't settled by the product spec and needed an explicit
decision: how to prevent the token from becoming (or being mistaken
for) authentication infrastructure, and how to guarantee single-use
under concurrent requests -- Milestone 0.8 found and fixed a real
TOCTOU race in refresh-token rotation
([Session-Management.md](../security/Session-Management.md#concurrent-rotation-milestone-08)),
and a BlueMoon Token consumption race would be the same class of bug
with a worse consequence (two friendships from one token, not just a
confused session).

## Decision

**Separate infrastructure module.** `infrastructure/social/blue-moon-token.ts`
duplicates the generation/hashing _pattern_ already proven for refresh
tokens (32 random bytes, SHA-256 of the lookup value --
`infrastructure/identity/refresh-token.ts`) but is a distinct file with
no import relationship to Identity's auth infrastructure. A BlueMoon
Token is never signed into a JWT, never creates a session, and never
authenticates anyone -- every Social route still requires an existing
authenticated session via Identity's unmodified `requireAuth`
middleware.

**Consumption is one atomic database statement, not check-then-update.**
`FriendshipRepository.consumeTokenAndCreateFriendship` performs a
single conditional `UPDATE blue_moon_tokens SET consumed_at = ...
WHERE token_hash = $1 AND owner_id = $2 AND consumed_at IS NULL AND
expires_at > now() RETURNING *`, inside a `db.transaction()` that also
creates the friendship row. If two requests race to consume the same
token, PostgreSQL's row-level locking guarantees exactly one `UPDATE`
succeeds; the loser's query returns zero rows, and the repository
returns `null` -- there is no separate "check if valid" step that
could go stale between check and write.

**Token consumption and friendship creation are one transaction.**
Both writes must succeed or fail together -- a token consumed with no
resulting friendship (or a friendship created without the token ever
being marked consumed) would violate "single-use" and "username +
token only" respectively. If the two users are already friends when a
valid token is consumed, the token is still marked consumed (it was a
valid redemption) but the friendship insert is `ON CONFLICT DO
NOTHING` -- idempotent, not an error.

**Generic error for every invalid-consumption case.** Unknown target
username, wrong token, expired token, and already-consumed token all
surface as the same `BlueMoonTokenInvalidError` (401) -- distinguishing
any of them would let an attacker enumerate usernames or probe token
state, the same reasoning as Identity's `InvalidLoginError`.

**Canonical friendship storage order, enforced at the database level.**
`friendships` stores the lexicographically smaller user id as
`user_a_id`; a check constraint (`user_a_id < user_b_id`) enforces this
and, as a side effect, makes a self-friendship impossible to insert at
all (a service-layer guard also rejects it earlier, with a clearer
error, but the constraint is the backstop).

**Both users must already be registered BlueMoon accounts.** Resolves
[PRD Open Question #4](../product/Product-Requirements-Document.md#open-questions):
no other account concept exists in this codebase (PINChat/Milestone 1.0
is unimplemented), so a BlueMoon Token can only target an existing
`users` row -- consuming one always requires an authenticated caller
(also a `users` row) and a resolvable target username.

## Alternatives Considered

- **Application-level check-then-revoke (Identity's `refresh_tokens`
  pattern before Milestone 0.8's fix):** rejected outright -- this is
  the exact bug class Milestone 0.8 found and fixed. Using it again
  here, now that the failure mode is documented, would be a known
  mistake, not a new risk.
- **Reusing `infrastructure/identity/refresh-token.ts` directly:**
  rejected -- a BlueMoon Token sharing a module with authentication
  token generation blurs the "not a credential" boundary the product
  spec is explicit about, even though the underlying crypto is
  identical.
- **Separate `db.transaction()` calls for consume and friendship
  create:** rejected -- reintroduces a window where a token could be
  consumed with no friendship created (e.g. process crash between the
  two calls), which is worse than the single-transaction cost of one
  repository method spanning two tables.

## Consequences

- `FriendshipRepository` owns writes to both `blue_moon_tokens` and
  `friendships` for the one operation that's inherently cross-table;
  `BlueMoonTokenRepository` is otherwise minimal (creation only).
  Documented explicitly in both files' JSDoc so this doesn't read as
  an accidental boundary violation later.
- No second connection pool: `app.ts` now builds one shared `Database`
  instance and passes it to both `createIdentityContainer` and
  `createSocialContainer`, rather than each container opening its own
  `postgres.js` client.

## Tradeoffs

A single generic error for every consumption failure mode is
deliberately less debuggable from the outside (a legitimate caller
with an expired token gets the same message as an attacker guessing
tokens) -- accepted for the same anti-enumeration reasoning already
established for login.

## Future Implications

If a "pending" or "requested" friendship state is ever introduced
(this milestone only implements immediate, token-gated connection --
no request/accept flow), the canonical-pair `friendships` table and
its check constraint would need to be revisited, since the current
model has no notion of a one-sided pending state.
